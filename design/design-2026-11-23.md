# Concordance App: Architecture and Design

Nov 21, 2026 · @Patrick Collins

The Concordance app is a local-first, peer-to-peer tool that carries the Concordance Charter: each member holds their own keys, every record is signed, and circles store and sync their data on members' phones and home hearths, with no central server. It is built spec first: every behavior is defined in a checkable specification before any code is written.

## Design principles

Every architectural choice traces back to a promise in the charter. If a design can't keep the promise, the design changes, not the charter.

| Charter promise | Engineering constraint |
| --- | --- |
| Open to all: anyone may join, and leave with their history | Keys live only on the member's devices; full export in an open format at any time; no barrier beyond a welcome from a member |
| Local rules: those affected decide | Rules are data the circle edits, not code; every peer enforces the current version |
| Freely given | No prices, balances owed or counts of giving in the data model |
| Need first | Allocation rules put need first; tests check worst-off outcomes, not only averages |
| Our own: our information and our network; what's private stays private | No central server or account; any peer can be replaced; private records encrypted end to end; open source |
| Equals together | Circles are independent units; federation is a signed agreement between circles, never a shared database |
| Held in trust | Land-trust accords make "never sold" a rule no vote can change |
| Bigger things need agreement everyone can live with | Every charter and accord version is content-addressed and signed; history is append-only |
| Anyone can take part without our tools | Works offline; a paper path for members without devices; plain language, large type, voice |
| Thank generously; everyone's gifts count | No scores, rankings or leaderboards anywhere in the data model or the interface |
| Words are provisions | In time, one Selewa text is both what members sign and what the app applies; no gap between words and behavior |
| The circle decides what it means | Promises are supported, never enforced; only protections are enforced; open phrases go to the circle; when the tool and the circle disagree, the text is fixed |

## Architecture at a glance

Phones, laptops and hearths are all equal peers running the same core; hearths add availability, and relays only help two peers find a path when home routers block a direct connection.

## Identity and keys

A member is a key, not an account. Devices act for the member through delegated keys, so losing a phone never means losing membership.

- **Member key (Ed25519):** created on the member's first device. It signs only rare, high-trust acts: authorizing or revoking devices, joining or leaving a circle, signing a charter version. Kept in the device's secure hardware where available.
- **Device keys:** each phone, laptop and hearth has its own key, which is also its Iroh endpoint address. The member key signs a delegation certificate for it, with the device's role (phone, hearth) and optional expiry.
- **Revocation:** a signed revocation record, gossiped to the circle. Peers reject anything the device signs after the revocation time.
- **Recovery, two routes:**
  1. A 24-word recovery phrase, written on paper at setup.
  2. Social recovery: the member key is split with Shamir secret sharing among trusted members chosen by the member (default 3 of 5). Shares are encrypted to each guardian's key; no guardian can use their share alone.
- **Key rotation:** a recovered or compromised member key is replaced by a new one, linked to the old by a signed succession record so the member's history stays theirs.
- **Paper members:** a member without a device gets a member key held by a chosen steward, who signs on their behalf only with recorded consent. The member can take the key over later.

## Data model

Each member keeps one signed, append-only log per circle. The circle's state (who belongs, which charter is current, what's been offered) is not stored anywhere as a master copy: every peer derives it by replaying the members' logs under the circle's rules.

**Every record carries:** author member key, signing device key, circle id, sequence number, hash of the author's previous record, timestamp, record type, body, signature. The hash chain makes a member's history tamper-evident: a gap or a fork in one author's log is itself evidence.

**v0 record types**

| Record | Signed by | Body | Visible to |
| --- | --- | --- | --- |
| `circle.founded` | Founding members | Circle name, first charter hash, visibility level | Circle |
| `device.authorized` / `device.revoked` | Member key | Device key, role, expiry | Circle |
| `member.introduced` | Newcomer | Introduction text, one offer | Circle |
| `member.welcomed` | An existing member | Newcomer's key | Circle |
| `accord.signed` | Member key | Version hash of the Charter or an accord | Circle |
| `member.left` | Member key | Optional note | Circle |
| `proposal.opened` | Any member | Draft document id, reason | Circle |
| `proposal.comment` | Any member | Text, optional concern flag | Circle |
| `proposal.agreed` | Facilitator, co-signed by members present | Proposal id, resulting accord version hash | Circle |
| `need.posted` / `offer.posted` | Any member | Text, optional expiry | Circle or named members |
| `thanks.given` | Any member | Recipient, text, visibility chosen by recipient | Recipient decides |
| `vouch.given` / `vouch.withdrawn` | Any member | Recipient, scope ("tools", "hosting") | Circle |
| `steward.recorded` | Steward | Paper member's act, consent note | Circle |
| `recovery.guardians` | Member key | Encrypted shares, guardian keys | Guardians only |

**Charter versions** are not records but content-addressed documents (BLAKE3 hash). Records point to them by hash, so "which version did you sign?" has one exact answer. The same holds for every accord (see Accords below).

**Deliberately absent:** counts of gifts, scores, follower lists, read receipts, location history.

## Sync and storage

Every device works fully offline and catches up when it meets another peer. Hearths make sure there is almost always a peer awake.

- **Connections: Iroh 1.0.** Peers dial each other by device key over QUIC, with hole-punching through home routers and relay fallback. Circles may run their own relay; the default is a list of community relays, never a single operator.
- **Announcements: iroh-gossip.** Each circle has a gossip topic derived from its id. New records are announced there; members subscribe on joining.
- **Log sync:** on connection, two peers exchange the latest sequence number per author and fetch what's missing. Logs are small and sync fully to every member device.
- **Documents and files: iroh-blobs.** Charter versions, attachments and exports are content-addressed blobs, fetched on demand and verified by hash.
- **Drafts: Automerge.** A proposal's draft is an Automerge document so members can edit offline and merge automatically. When agreed, the draft is frozen into a charter version blob.
- **Hearth storage:** hearths hold a full copy of every log and blob for their circles. Private material (care records, guardian shares) is encrypted before it reaches a hearth, so a host can't read what lives in their home.
- **Replication target:** v0 aims for every record on at least three hearths in different homes. Erasure coding across hearths (any k of n rebuilds the data) is deferred to v1, once circles hold more than text.
- **Phones:** keep their own circle's logs in full, plus blobs they've opened; everything else is fetched from hearths when needed.

## Rules and validation

There is no server to enforce rules, so every peer checks every record it receives, the same way, and drops what fails.

**Two layers of checks**

1. **System checks, fixed in the protocol:** valid signature; device authorized by the author at the time of signing and not revoked; sequence and previous-hash consistent; record type known; body matches its schema.
2. **Circle rules, set by the circle as data:** for example "a newcomer becomes a member when one member welcomes them," or "a proposal is agreed when no member present records a concern." Each rule is a small declarative entry in the circle's rule book, versioned and signed like the charter.

**Determinism.** A rule's result may depend only on the records it reads, never on the clock, the network or the device. Two honest peers with the same records always reach the same state.

**Spirit over thresholds.** The charter avoids hard numbers, so most v0 rules record and surface rather than block: the app shows that a request has gone unanswered or that a member has gone quiet, and leaves the response to people. Hard blocks exist only where safety or integrity needs them: unsigned records, revoked devices, care records opened by someone not named.

**Promises, not commands.** Provisions are grouped as promises (the tool reminds and records, never blocks), freedoms ("we can"), requests ("we ask"), hopes, and protections. Validation blocks only to keep a protection, never to enforce a promise. See Selewa and the meaning layer.

**Forks are allowed.** If members can't accept a change, they can start a new circle from any charter version. A fork is a new circle id with a `circle.founded` record that cites its parent; members' histories travel with them.

**Later:** a sandboxed rule engine (WebAssembly) so circles can share richer rules within their accords without anyone running untrusted code.

## Accords

The Charter is the root accord; every other accord grows from it or from another accord. A circle adopts the Charter first, adds the accords that fit its purpose, and makes each one its own. New kinds of circle come from writing a new accord, not new software: the test that Concordance is a general commoning system.

**Three kinds of accord**

- **Purpose accords** say what a circle does (Care, Garden, Land Trust).
- **Practice accords** change how any circle works once adopted, and apply to everyone in it (Anonymity, Open Dispute Hour, Pattern Sharing).
- **Linking accords** work between circles (Federation, Crisis Response).

**The accord tree**

- **The Charter** (root accord)
  - **Everyday accords:** Mutual Aid, Gifting, Work Day
  - **Purpose accords**
    - **Care** (its safeguarding is inherited by all beneath it): New Parents, Childcare, Youth, Elders, Caregivers, Disability and Access, Farewell and Grief
    - **Health and healing:** Recovery and Peer Support (requires Anonymity), Listening, Living with Illness, Community First Aid
    - **Food and water:** Garden (with Seed Library), Community Kitchen, Water
    - **Land and shelter:** Land Trust (with Build and Housing, Nature Stewardship)
    - **Things, spaces and movement:** Tool Library (with Repair), Shared Space, Lifts and Transport
    - **Learning and culture:** Knowledge Commons (holds the accord library), Study Circle, Apprenticeship, Creative
    - **Livelihood:** Skill Share, Worker Cooperative, Open Source Project
    - **Infrastructure:** Energy, Connectivity, Compute
    - **Peace and justice:** Welcome, Rights (requires High Risk), Peacemaking
    - **Meaning:** Faith or Practice
    - **Resilience:** Preparedness
  - **Practice accords:** Open Dispute Hour, Anonymity (with High Risk), Bridge, Common Purse, Mentoring, Pattern Sharing (not available with Anonymity or High Risk)
  - **Linking accords:** Federation (with Crisis Response, which requires Preparedness; Seeding; Exchange)

Safety flows down the tree: every Care accord inherits safeguarding, and every Rights circle inherits High Risk. "Requires" links keep combinations sound. A new circle needs only the Charter, Mutual Aid, Gifting and Work Day; the rest grows when needed. Every accord passes the five tests, so there is no marketplace or ranking accord.

**Words and provisions** Each accord carries the same agreement in two forms, as Creative Commons licences do: the words members read and sign, and structured provisions the app reads. Provisions combine only a fixed vocabulary of building blocks (resources with uses, records, roles, declarative rules, privacy levels, prompts and standard views), so an accord can never run arbitrary code. When a circle adopts an accord, the app assembles its screens and rules from the provisions. Example, the Work Day accord:

```
grows-from: charter v2 or later
kind: everyday
resource: task slots (shared), tools and materials (offered)
records: workday.proposed, workday.joined, item.offered,
         workday.held, thanks.given
roles: host, task lead, meal lead, safety
rules: a household agrees before work on its home;
       safety briefing before tool use
prompts: reminder the day before; suggest the next one afterward
views: work day page, task board, meal list
privacy: circle (open to invited guests)
```

Words and provisions must match: when either changes, the app shows the provision change in plain language beside the wording, and members agree to both. An AI assistant may draft provisions from the words; people check and agree them. Provisions merge down the tree, and those from the Charter (safety, free exit, export) can't be switched off.

**Storage** An accord is a small bundle: `accord.toml` (name, version, grows-from range, requires, licence, change note, provisions) and `words/<language>.md` for each translation, all sharing one language-neutral set of provisions. Its BLAKE3 hash, over a canonical form, is the version's identity. The shared accord library is a Git repository in the Knowledge Commons, hosted on Concordance: each accord a folder, each agreed version a commit, adapted versions from different circles and cultures as branches. Phones keep the accords their circles use; hearths keep every version ever adopted. No version is deleted while anything points to it, and none is edited in place.

**Adoption and signing**

- **The Charter:** adopted at founding; every member signs it on joining.
- **Purpose accords:** the circle adopts by agreement; members who take part sign; others aren't bound and can't take part until they do.
- **Practice accords:** apply to the whole circle once agreed; members acknowledge them, and anyone can object before agreement.
- **Linking accords:** the circle signs as a whole, by agreement.
- **Roles** (safety lead, steward) are individual commitments the circle agrees to, where required checks are recorded.
- Records: `accord.adopted`, `accord.signed`, `accord.version.agreed`.

**Creating a new accord**

1. Notice a need, and look in the library first; adapt an existing accord if one fits.
2. Start from the nearest accord, which the new one grows from.
3. Write the words together, as an Automerge draft.
4. Draft provisions from the words, with AI help, checked by members.
5. Automatic checks: only known building blocks, nothing overriding the root, requirements met, the five tests passed.
6. Try it, if it's safe to try; adjust.
7. Agree, sign and adopt; then, if the circle wishes, share it to the library under an open licence. Library stewards review lightly, and carefully for anything touching care, children, safety or high-risk use.

Anyone can write an accord and use it in their own circle without permission. When an accord needs something the building blocks can't do, it becomes a behavior spec for the stewards' circle, and the new building block is released for everyone.

## How the charter and accords evolve

A charter that needed every circle's agreement to change would never change. So three things change in three different ways.

1. **A circle's own charter and accords** change whenever its members agree, by proposal, listening and agreement. Each version is fixed once agreed, which makes change visible rather than preventing it.
2. **The shared root accord in the library changes by adoption, not by vote.** Library stewards publish new versions, informed by what circles have adapted and learned; each circle chooses whether and when to adopt one. Old and new versions coexist, as Creative Commons licence versions do. Good changes spread because circles see them work.
3. **What circles share in order to federate is a small core,** the seven principles in any wording, not identical text. Circles on different charter versions federate freely; the principles themselves evolve slowly, by agreement among federated circles.

**Keeping the rest from locking it in**

- Accords declare a range ("grows from charter v2 or later"), not one exact version; a new root version flags only real conflicts.
- Signatures don't expire: members sign a newly adopted version when they next open the app; their signature on the old version stays valid for the time it applied, and not having signed yet is never grounds for removal.
- Each circle revisits its charter regularly; library stewards gather what circles have learned once a year.
- Forks are welcome: many versions side by side is healthy, not a failure.

## Circles in different settings

The app is built for small groups; federation, not large circles, handles scale. These ranges are estimates from comparable groups (Kudumbashree's neighborhood groups, study circles, mutual-help fellowships) and research on stable relationships, to be replaced by pilot data.

- **Circle size:** typically 10 to 40 members, average perhaps 20 to 30; at least about 5 to share the work; about 150 at most, where members stop knowing each other by name.
- **Circles per person:** most members 1 to 3; very engaged members 4 to 6; rarely more than 8 to 10. A common pattern is one place-based home circle, one to three purpose circles, and federations experienced through circles.
- **In person or online:** place-based circles mostly meet in person and coordinate in the app; purpose circles with spread-out members are often mostly online; most end up hybrid.

|  | Rural | Suburban | Urban |
| --- | --- | --- | --- |
| Circle covers | A village, valley or township | A few streets, a school, a congregation | A building or a block |
| Typical size | 10–30 | 15–40 | 10–40, higher turnover |
| Circles per person | 1–2, each doing many things | 2–3 | 2–5, including interest and identity circles |
| Builds on | Churches, granges, volunteer fire, kin | Schools, faith groups, parents, retirees | Tenant groups, mutual aid, diaspora and faith communities |
| Key accords | Lifts and Transport, Water, Land Trust, Work Day, Preparedness | Tool Library, Childcare, Elders, Work Day | Shared Space, Welcome, Bridge, Mutual Aid, Community Kitchen |
| Main challenge | Distance and weak connectivity | Isolation and lack of time | Turnover, anonymity, many languages |

**Design consequences:** offline-first and local-only sync matter most in rural areas; onboarding, renewal and the Bridge accord in cities; quick, small contributions in suburbs. Belonging to several circles must be easy, with one view of needs and offers across them while each circle's privacy stays separate.

## Lessons from cooperative traditions

Concordance should feel like a natural extension of the world's long-lived cooperative practices, not a replacement for them. Four design consequences follow.

**New accords (after v0)**

- **Work day** (after gotong royong, minga, dugnad): a task, a date, a shared meal, an open invitation.
- **Farewell and grief** (after burial societies and iddir): meals, visits and practical help for a member's family through illness or death; private by default and guided by the family's wishes.
- **Open dispute hour** (after the Valencia Water Tribunal): a regular, short time when anyone can bring a disagreement to be heard quickly and simply.

**Guarding against "us versus them"**

- No comparisons or rankings between circles.
- No shared blocklists between circles beyond genuine safety concerns.
- Federation makes helping other circles easy, so the natural movement is outward.

**Local names and forms.** Circles name their practices in their own words, and the accord library holds versions contributed by circles in different cultures.

**Designed for renewal.** A quiet circle can be revived from its records; experienced members can take a mentoring role for new circles; a shared archive keeps each circle's stories when its founders move on.

**Bahá'í practice.** Bahá'í consultation seeks the truth together rather than winning an argument, and Bahá'í elections have no candidates or campaigning. Bahá'u'lláh's call for a universal auxiliary language, taught beside every mother tongue, is one inspiration for Selewa.

## App design

The app should feel like a quiet notice board for people who know each other, not a social network. Nothing in it competes for attention.

**Built with:** Tauri 2, one codebase for Android, iOS, Windows, macOS and Linux. A Rust core holds Iroh, Automerge, the record log and validation; a small web interface sits on top. The same core runs headless on hearths.

**v0 screens**

| Screen | What it does |
| --- | --- |
| Welcome | Create your key, write down the recovery phrase, choose guardians later |
| Join a circle | Scan an invitation code, read the charter, introduce yourself, sign |
| Circle home | This week's needs and offers, upcoming gathering, people who may want a check-in |
| Needs and offers | Post, answer, and mark done; replies go privately to the poster by default |
| Charter | Current version, history of versions with what changed and who signed |
| Proposals | Open a change, edit the draft together, comment, record agreement |
| People | Members, welcomes and vouches; no counts or rankings |
| Me | My devices, my guardians, my thanks (shown or private), export everything |
| Hearth | Pair a hearth by scanning its code; see that it's healthy |

**Interface principles**

- **No feed, no badges, no infinite scroll.** Lists end. Notifications are a gentle daily summary unless something is urgent.
- **Gentle prompts instead of rules:** "Ana asked for a lift yesterday and hasn't had a reply"; "You haven't heard from Joseph in a while."
- **Plain words:** "sign," "welcome," "leave"; never "keys," "hashes" or "nodes" on the main screens.
- **Accessible from the start:** large text, screen readers, high contrast, translation of the interface and of the charter.
- **The paper path:** a steward screen to record a paper member's agreement or request, with their consent noted.

## The hearth

A hearth is a small, silent, always-on computer that a member plugs in at home. It's just another peer with the member's delegated key: it has no authority, only availability.

- **Hardware:** a low-power single-board computer or a recycled mini PC, with an SSD, no fan, and wired networking. A reference image targets one widely available board first; recycled hardware follows.
- **Software:** a minimal Linux image with the Concordance core running headless, a read-only system partition, and encrypted storage.
- **Pairing, no configuration:**
  1. Plug in power and the router.
  2. On first boot it creates its device key and shows a code (printed label or small screen).
  3. The member scans the code with the app; the member key signs a delegation with role "hearth".
  4. The hearth joins the member's circles and starts syncing.
- **Updates:** signed releases, verified by the hearth before installing, with automatic rollback if the new version fails to start. A circle can choose a slower update channel.
- **What it does in v0:** keeps every log and blob for its circles; relays for phones that are asleep; holds encrypted guardian shares.
- **Later:** erasure-coded storage across hearths (v1); sandboxed shared compute such as local translation, needs-and-offers matching and a local AI model (v2).
- **When a hearth is lost or stolen:** the member revokes it from the app. Everything on it is encrypted or replicated elsewhere, so nothing is lost and nothing is exposed.

## Shared compute

AI, translation, builds and storage will need far more than one small hearth per home. Compute is treated as a commons, governed like any other scarce resource.

**Sources, nearest first**

1. **Pooled hearths:** many small tasks spread across idle hearths (translation, matching, search, small models).
2. **Community compute hearths:** larger machines with graphics processors, hosted where communities gather (libraries, makerspaces, co-ops, schools) and shared by a federation.
3. **Members' idle computers:** contributed with consent when unused, following volunteer-computing precedents such as Folding@home and Petals.
4. **Partners at the boundary:** universities, public research computing and nonprofits, for heavy jobs such as training a base model.
5. **Using less:** small specialized models, retrieval instead of bigger models, and work scheduled only when useful.

**Allocation:** need first (crisis translation and safety messages), then turns. A host's own use always comes first, and hosts set how much they share, when and for which circles. Heavy work runs when renewable power is available.

**Rules**

- Private content is processed only on the member's own or their circle's hearths. Volunteer machines and partners handle only public, commons or encrypted work.
- Every task runs in a sandbox (WebAssembly or containers) with no access to the host's files.
- Results from untrusted machines are verified, for example by running the same work on two machines, before anyone relies on them.

**Phasing:** v0 needs no shared compute; v1 adds pooled hearths and a few community compute hearths; v2 adds a compute-sharing protocol across federations and volunteer machines.

## The Concordance AI

The AI is shaped by what circles share freely in the commons, grounded at answer time in each circle's own content, and never trained on anything private.

**Three layers**

1. **An open base model trained on open, consented text,** with its training data published, such as models built on public-domain and openly licensed collections like EleutherAI's Common Pile.
2. **Adapted on the knowledge commons:** the charter and accords in every language, practices and stories that circles contribute under an open licence, each with a signed consent record.
3. **Retrieval for circle content:** when a member asks something, their hearth looks up only what that member may already see and passes it to the model for that answer. Nothing private is ever trained into the model's weights.

**Why retrieval, not training, for private content:** what is trained into a model can't reliably be removed. Retrieval keeps leaving real, lets records fade, and makes the model's access follow each member's permissions.

**Governance:** the model is a commons, stewarded like the code. Its training data, adaptations and releases go through the stewards' circle, are published openly and can be forked.

**Where it runs:** small models run on hearths and community compute hearths; adaptation runs on contributed compute; training a base model happens with partners at the boundary.

## Language and translation

Most of the world's cooperative traditions live in languages technology serves poorly. Concordance treats every language as equal.

**The charter**

- **Translated and adapted by people** from circles that will live by it; machine translation may draft, people decide. Translators may use local images and words (*dugnad*, *minga*, *harambee*) where they say it better.
- **Every language version has equal standing.** There is no English master copy: each translation is a signed record pointing to the charter version it translates, and drift in meaning is resolved by proposal like any other change.
- **A translation commons** holds translations of the charter, accords, stories and the app interface, open to every new circle.

**Circles across languages**

- **Translation on the hearth:** messages, needs and offers translated by a local model, so nothing private leaves the circle.
- **The original is always one tap away,** so translation never puts words in anyone's mouth.
- **Bridge members:** bilingual members take a recognized role, especially in decisions.
- **Decisions slow down:** proposals appear in every member's language, and listening takes longer on purpose. The charter, safety messages and decisions are always checked by a person.

**Beyond written words**

- **Voice:** needs, offers and introductions can be spoken and played back; the charter can be heard as well as read.
- **Symbols:** simple icons for common needs (a meal, a lift, a repair, a visit).
- **Sign languages:** video introductions and the charter in sign languages, made by deaf members.
- **All scripts from v0:** right-to-left, complex and minority-language scripts supported from the start.

**Selewa, Concordance's own language.** Alongside every mother tongue, Concordance grows an auxiliary language of its own. *Selewa* ("hearts together") is Concordance's name for itself in that language; in English text we say Concordance, and write Selewa only for the language itself. The seed (sounds, grammar and the first hundred roots) is in [the Selewa seed](../accords/selewa/words/en.md); how it fits the design is the next section.

## Selewa and the meaning layer

Selewa's core is a meaning layer: roots and grammar identified by meaning, not by spelling or sound. Scripts and voices are surfaces over it. This lets one text be read in any script and spoken in any accent, and lets an accord's words and its provisions become the same text.

**Layers**

1. **Core:** roots defined in the semantic primes (about 65 meanings found in every language studied); each root is a signed `word.coined` record identified by its hash, so meanings never drift silently.
2. **Scripts:** Latin, Arabic, Devanagari, Hangul, Ge'ez, a native Selewa script and Braille, each a reversible mapping table.
3. **Voices:** regional pronunciations that keep the same sound distinctions.
4. **Signs:** a signed form on the same core.

Each becomes an accord: Selewa Core, plus script and voice accords that circles adopt as they use them.

**Sentences are trees.** A sentence is stored with explicit roles (who does what, to whom), so each voice may choose its own word order and the meaning stays the same.

**Two modes.** *Precise* Selewa, for commitments and accords: every role explicit, no ambiguity. *Open* Selewa, for song, story and prayer. Both use the same roots.

**Words become provisions.** A text in precise Selewa can be compiled into an accord's provisions, so the words people sign and the rules the app applies are one text. Accords are built from promises, not commands:

| Kind | What the tool does |
| --- | --- |
| We promise | Reminds, records, celebrates; never blocks |
| We can | Makes it easy |
| We ask | Shows the request; anyone may say no |
| We hope | Keeps it visible |
| Protection | Enforced, and only to protect people (privacy by encryption) |

Example, from Work Day: *"We promise: each season, we gather for one work day. Whoever can, comes. Whoever cannot, is not blamed."* compiles to a recurring event, an optional RSVP, thanks for those who came, and a protection: no record of absence.

**The circle decides what it means.** Open phrases such as "when we can" or "fairly" compile to a single instruction: the circle decides. If the tool's reading and the circle's understanding ever differ, the circle is right and the text is fixed. This is the reverse of "code is law."

**Signing meaning.** Members sign the hash of the canonical meaning tree; each language version is a view of what was signed. Rendering must be deterministic and checked by more than one independent renderer, so no one can show a gentle translation of a harsher meaning.

**Writing an accord becomes writing.** A member writes sentences in their own language; the app shows a paraphrase back ("Did you mean…?"); they confirm; it compiles, the simulator tries it, and the circle adopts it. Amendments show as changes in meaning. Conflicts with accords the circle already holds are flagged before adoption.

**The AI is never in the trust path.** It helps draft and suggests parses. A person confirms every parse, and after that only the deterministic compiler acts.

**New threats.** Ambiguity attacks (text crafted to parse differently than it reads) and rendering attacks (a translation that misrepresents what was signed). Defences: the paraphrase round trip, signing the canonical tree, and several independent parsers and renderers that must agree.

**Bootstrapping, as a compiler does.** Stage 0: the grammar written in English and other host languages, reviewed by native speakers of many languages so no single one leaks into the result. Stage 1: the Charter written in Selewa. Stage 2: the grammar and dictionary written in Selewa. Stage 3: someone who learned only from the Selewa grammar rewrites the Charter, and it matches. For accords: words and `accord.toml` written separately, then Selewa compiled into TOML, then the Selewa text is the accord and the TOML is generated.

## Faith and culture

Concordance aims to be compatible with every faith and none, as far as that is possible. The Charter says: people of every faith and none are welcome, and we honor each other's beliefs without pressing our own.

- **A neutral root.** The Charter uses no single tradition's language, so anyone can sign it without setting their own faith aside.
- **Holy days and prayer times.** The app knows members' sabbaths, festivals and prayer times (shared only if they choose) and avoids them when suggesting gatherings and work days.
- **Shared meals.** Meal sign-ups can mark dishes as halal, kosher, vegetarian or suitable during fasts.
- **No recruiting.** Circles are not a place to recruit for or against any religion.
- **Faith communities keep their own life.** A congregation, sangha or prayer group adopts the Charter through the Faith or Practice accord, alongside its own traditions.

**Hard cases, named in advance**

- **Single-gender gatherings:** the network stays open to all, while individual circles may serve a particular group by choice, as women's or men's groups already do.
- **Differing teachings on sexuality and family:** the Charter's "never against anyone" and safety rules mean no member may be excluded or harassed for who they are, even where circles hold different beliefs.
- **Mixed circles:** members of different faiths share a circle by respecting each other's practices rather than adopting any one set.

## Security and privacy

The people most likely to need a circle (survivors, the isolated, people under pressure from those around them) are also the most at risk if it leaks. Privacy is the default; openness is a choice.

| Threat | Protection |
| --- | --- |
| Lost or stolen phone or hearth | Device revocation; encrypted storage; member key in secure hardware |
| Lost member key | Recovery phrase or 3-of-5 guardian recovery; signed succession to a new key |
| Impersonation or fake members | Joining needs a welcome from an existing member; vouches are scoped and withdrawable |
| A member rewriting their past | Hash-chained logs: a changed or forked history is detectable by every peer |
| Eavesdropping on the network | All traffic encrypted by QUIC; private records encrypted end to end to named recipients |
| A curious hearth host | Private material reaches hearths only in encrypted form |
| Hiding a circle's existence | Private circles use unguessable topic ids and never appear in any directory |
| Malicious software update | Releases signed by multiple maintainers; hearths verify before installing |
| Someone harming a child or vulnerable adult | The charter's safety rule: concerns go to the chosen safety person; care roles need the checks the law requires |

**Metadata matters too.** Relays see which devices connect, not what they say. Circles that need more protection can run their own relay, or connect only peer to peer.

**Anonymity, as an explicit promise.** Recovery groups and other peer-support circles need stronger anonymity than most, and Concordance promises it:

- **Pseudonyms are first-class.** A member key needs no real name; a member can use a different name in each circle, and nothing links them unless the member chooses.
- **Private circles are invisible** to anyone outside them: no directory entry, no discoverable topic, no federation listing unless the circle opts in.
- **No record reveals who attends what,** even to a hearth host: membership and attendance in private circles are encrypted to members only.
- **No contact discovery.** The app never uploads address books or suggests people from outside the circle.

**Legal duties.** Encryption and data laws vary by country, and some governments are debating message scanning. The design keeps content end-to-end encrypted and gives circles no central point a court can compel.

## High-risk and rights circles

Where governments are hostile to independent self-organization, no tool can make people fully safe. The aim is to reduce risk, never to promise safety, and to let people judge for themselves.

**Honesty first**

- A published threat model, in plain words and every language, saying what Concordance protects against and what it doesn't.
- Risks discussed with members before they join a high-risk circle.
- Sometimes the safest tool is none: the circle can meet and care without the app.

**The High Risk accord** (grows from Anonymity)

- Minimal traces: no stored member lists, no contact uploads, as little metadata as possible.
- Records that fade after a short time.
- Local-only sync over Wi-Fi or Bluetooth, with no internet.
- Small, separated circles, so exposing one doesn't reveal others.
- Emergency revocation of a seized device from another, and quick wiping of app data.
- Circles may run without hearths, or encrypt them so a seized one reveals nothing.
- Support for established censorship-circumvention tools such as Tor.
- Distribution outside app stores (for example F-Droid), with reproducible builds.

**The Rights accord** (requires High Risk) Support for families of the detained, accompaniment, welcome and sanctuary, know-your-rights learning, rapid response and solidarity across borders; a named safety lead and an arrest-or-seizure plan; links to partner organizations for legal, medical and digital-security help; strong rest and debrief practices. Rights circles protect people's dignity, everyone's including opponents': firm against injustice, never against persons. Documenting abuses for courts uses specialized tools (such as Tella or Uwazi) and professional organizations, not Concordance.

**Responsibilities of the project**

- Outside security audits before high-risk use is encouraged; until then, the app says plainly that it is not yet recommended for high-risk use.
- No backdoors, ever, written into the stewards' circle charter.
- Stewards and release signers in several countries.
- Human rights organizations (such as Access Now and Front Line Defenders) invited as advisors first, not as adopters; pilots only with communities they know and can support.
- High-risk use comes last in the roadmap, after an audited track record in ordinary circles.

## Spec-driven development

The specification is the source of truth; code is one implementation of it. Any team, or any AI agent, should be able to build a compatible Concordance from the specs alone, and prove it by passing the conformance suite.

**Four layers of spec, each tracing to the one above**

1. **The charter:** what we promise each other.
2. **Design principles:** each promise as an engineering constraint (the table at the top of this doc).
3. **The protocol spec:** precise promises about how the software behaves, so that every app built for Concordance can talk to every other and keeps the charter's promises to members. It binds code, never people. It covers record formats, signatures, delegation, sync messages, validation steps, rule-book schema. Versioned; changes follow the same proposal process as the charter, among maintainers.
4. **Behavior specs:** scenarios in Given/When/Then form for every user-visible behavior, e.g. *Given a member has lost their phone, when three of five guardians approve, then the member's key is restored and their history is intact.*

**Checks that run on every change**

- **Conformance suite:** test vectors for every record type, signature and validation rule; any implementation must pass all of them.
- **Determinism tests:** replay the same records in random orders and from random partial states; every run must reach the same circle state.
- **Network simulation:** many simulated peers with partitions, offline phones and lost hearths; sync must converge without loss.
- **Fuzzing** of every parser and validator.
- **Traceability:** every test cites the spec clause it checks, and every spec clause cites the charter promise it serves. An untraced clause is questioned; an untested clause blocks release.

**How work flows**

1. A need is written as a behavior spec, in plain language, and reviewed by people from a circle, not only developers.
2. Protocol changes are proposed, discussed and agreed before any code.
3. Code is written by people or AI agents against the agreed specs, with a human reviewing every change.
4. The checks above gate every merge; architecture decisions are recorded as short decision records.

**Repository layout:** `charter/`, `spec/protocol/`, `spec/behavior/`, `spec/vectors/`, `decisions/`, `core/` (Rust), `app/` (Tauri), `hearth/` (image), `sim/` (network simulator).

## The simulator

A long-lived simulator of society tests whether Concordance's virtuous cycle holds (help builds trust, trust brings giving, visible results bring invitations, circles split and federate, trust land makes gains permanent) and what breaks it. It is built test first, runs the real accord engine, and is fed over time with real patterns from circles that choose to share them.

**Architecture**

- **Shared core (Rust):** the same accord engine and record validation as the app, so simulations test the real accords. A Python layer, through Rust–Python bindings, for scenarios, experiments and analysis.
- **Synthetic populations** for real places, built from census and survey data (iterative proportional fitting), with household, kin, neighbor, work, faith and friendship ties.
- **Environment and shocks:** geography from OpenStreetMap, public services, cost of living, holy days; individual shocks (illness, job loss, birth, death) and shared ones (recession, heatwave, flood, outage).
- **Economy as conditions, not a full model:** household facts (income, time use, housing, care burden, connectivity) and social facts (trust, participation, networks) matter most; macroeconomics enters only as shocks, with feedback into the wider economy deferred to later versions.
- **Time:** daily steps, hourly during crises; every action written to an event log.

**Agents**

- **Rule-based agents** for towns and cities: time budgets, generosity, trust, fatigue, reciprocity; joining follows complex contagion (an agent joins after enough close ties have), which Damon Centola's research suggests spreads committed behavior best through tight clusters.
- **AI-model agents** for small samples, with personas and a fixed action set (help, ask, join, leave, object, propose). Their agreeableness suits the seed phase of likely early adopters, so they get time budgets, fatigue and some strong disagreements; more varied, skeptical, time-poor agents test crossing the chasm to the pragmatic majority. Their behavior is summarized into rules for the large-scale engine.

**Metrics:** unmet needs, loneliness, wellbeing, burnout, adoption, circle survival, inequality of unmet needs between groups, cross-group ties, trust, land in trust, always including worst-off outcomes as well as averages.

**Testing, non-binary where it should be**

- **Binary:** rules and invariants (time is never created; a tool is in one place at once; trust land never leaves trust); reproducibility from a seed; reproducing Schelling's segregation and Axelrod's cooperation results.
- **Statistical:** Concordance claims as Given/When/Then scenarios over many seeds, checked by ranges, confidence intervals and worst-case bounds.
- **Calibration:** group sizes, volunteering rates and growth roughly match real data.
- **Regression:** every change to the Charter, an accord or the app reruns the simulation suite; changes that worsen burnout, exclusion or inequality are flagged before release. Results inform judgment; real pilots are the acceptance tests.

**Real data through the Pattern Sharing accord** Patterns, never people. Circles opt in by agreement and choose each item shared (circle health, responsiveness, accords used, crisis response, optional anonymous wellbeing answers, land in trust). Figures are computed on the circle's hearths; only aggregates leave, with minimum group sizes and differential privacy. Never shared: names, message content, who helped whom, attendance, precise locations. Not available to circles under Anonymity or High Risk. Data is used only to improve Concordance, never sold, never given to authorities, never used to judge circles; results are published openly. A pattern steward role answers members' questions. Records: `pattern.adopted`, `pattern.item.changed`, `pattern.sent`, `pattern.withdrawn`.

**Build order**

1. Spec, with the first claims written as tests.
2. A minimal town of 5,000 rule-based agents with the Charter and Mutual Aid.
3. The shared accord engine running real provisions.
4. Adoption, splitting, mentoring and whole communities adopting together.
5. Crises and federation.
6. AI-model agents for the seed phase and the chasm.
7. Synthetic populations of real rural, suburban and urban places, calibrated.
8. Continuous comparison with real circles through Pattern Sharing.

The simulator lives in `sim/` beside the app and is built alongside the core library, since both use the accord engine.

## Self-hosting and governance

Concordance hosts its own complete definition, and the project is governed by its own charter. The first real circle on Concordance is the stewards' circle that builds it.

**The complete definition** is everything needed to understand, rebuild and verify Concordance with nothing else: the charter and its history, the design principles, the protocol and behavior specs, conformance vectors, all source code, a reproducible build recipe, decision records, accords and translations.

**Native Git hosting, borrowing Radicle's ideas.** Concordance already has signed records, content-addressed blobs, a peer network and hearths, so Git is a thin layer on top. Radicle's MIT/Apache licence lets us borrow its ideas and code where useful.

- **Git objects:** an ordinary local repository on each device, using gitoxide; commits and files sync between peers as Git packs over Iroh.
- **Branches as signed records:** `repo.ref.updated` says which commit a branch points to, signed by whoever moved it, and every peer checks it against the circle's rules.
- **Who can move main:** a rule in the stewards' circle's rule book, e.g. "main moves only for an agreed proposal, signed by two stewards." The canonical version is defined by named stewards' signatures, not by whoever runs a server (Radicle's best idea).
- **Changes and reviews:** a code change is a proposal pointing at commits; reviews are proposal comments.
- **Plain Git for developers:** a `git-remote-concordance` helper so `git push` and `git pull` work as usual.
- **Hearths as seeds:** hearths hold repositories alongside their circles' records.

**One governance for everything.** A code change, a spec change and a charter change follow the same path: proposal, listening, agreement, signed record. A release is a signed record from several stewards, and hearths install only releases signed under the stewards' circle's rules. Anyone can fork, so no group of stewards can capture the project.

**Stewards are trusted servants; they do not govern.** The phrase comes from Alcoholics Anonymous's Twelve Traditions, which have held a worldwide voluntary network together for decades without anyone in charge. Anyone may contribute without permission. Stewards grow into the role through contribution, are agreed by the stewards' circle, look after one scoped area, rotate, and follow the same gentle steps as everyone else. Release signing is the one firm rule: every release needs more than one signer, ideally in different homes and countries, with keys on dedicated hardware. The founder starts as the first steward and shares signing as soon as a second trustworthy signer exists.

**Bootstrapping**

1. Start the repository in ordinary Git, with a read-only mirror on a nonprofit host such as Codeberg so newcomers can find it.
2. Run the stewards' circle by the charter from day one, recording decisions in the repository.
3. Once native Git hosting works, move the repository, decisions and releases onto Concordance.
4. From then on, every hearth can rebuild and verify the software it runs.

**Where the care goes:** peer authentication and ref validation get an outside security review before anyone relies on them (Radicle's 2026 vulnerabilities were in exactly this area); rejected pushes, conflicting ref updates and revoked stewards get explicit rules and conformance tests.

## v0 scope and the spike

v0 does exactly what the charter needs and nothing more: identity, joining, signing, proposals, needs and offers, export, and one hearth per circle. v0 ships the Charter and three everyday accords: Mutual Aid, Gifting and Work Day. Each step below has a gate that must pass before the next begins.

1. **Specs first:** protocol spec for identity, delegation, records and validation; behavior specs for the v0 screens; first conformance vectors. *Gate:* a second developer can explain the protocol from the spec alone.
2. **The spike:** two phones and one hearth. Create member and device keys; connect across different networks; publish a charter version, sign it on one device, verify it on another; sync after one device was offline; recover a key from 3 of 5 guardians. *Gate:* all five work, and the determinism tests pass.
3. **Core library:** the Rust core with logs, validation, sync and rules as data. *Gate:* conformance suite and network simulation green.
4. **Native Git hosting:** signed ref records, pack sync over Iroh, the `git-remote-concordance` helper, and hearths seeding repositories. *Gate:* the stewards' circle moves the Concordance repository onto Concordance, and an outside reviewer has checked peer authentication and ref validation.
5. **App v0:** the nine screens, in English first, with large-text and screen-reader support. *Gate:* someone who has never used it joins a circle and signs the charter unaided.
6. **Hearth image:** reference board, zero-configuration pairing, signed updates with rollback. *Gate:* a non-technical member plugs one in and pairs it in under a coffee break.
7. **Pilot:** three different local groups use v0 for three months. *Gate:* each group decides to keep using it.

**Not in v0:** resources and scarcity rules, federation, care-circle records, erasure coding, shared compute, translations beyond English. Each waits until real circles ask for it.

**Locked in now, so Selewa can follow later.** v0 accords use a canonical, hash-identified encoding, so signatures can later move onto meaning trees, and their provisions are already grouped as promise, can, ask, hope and protection.

**After v0: Selewa milestones**

1. **Selewa seed and compiler:** the seed reviewed from many host languages, and the Work Day accord written in precise Selewa and compiled to provisions. *Gate:* the compiled provisions match the hand-written `accord.toml`, and a circle confirms the paraphrase says what they mean.
2. **Accords written in Selewa:** new accords written as Selewa text, with TOML generated. *Gate:* a member with no programming background writes a working accord that a circle adopts.
